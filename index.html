CookMem

CookMem is a general-purpose memory context and allocator written in C++11. It can be cleaned up quickly by freeing segments rather than freeing allocations individually.

Unlike projects such as nedmalloc, which is intended to replace malloc / free in multithreaded applications, CookMem focuses on single-thread performance. It is intended for use within a thread in an MPP process, avoiding synchronization costs for most allocations and deallocations. There are other use cases as well.

CookMem separates the logic for obtaining large memory segments, allowing users to easily create a version of the memory context for their specific needs.

The algorithms and some code used here are based on dlmalloc. I took the time to understand dlmalloc and rewrite its logic in C++. Some key calculations remain the same as in dlmalloc because there is no need to reinvent the wheel.

Performance

The performance of CookMem is comparable to, if not faster than, dlmalloc. Neither dlmalloc nor CookMem uses locks. For CookMem, I also tested red-black tree (RB-tree) which is the default, and AVL-tree backend.

An interactive chart of these results is available with the documentation.

Each test was run 5 times. For each column, the best and the worst times were dropped and the remaining times were averaged. The numbers are in seconds.

Use Cases

Avoiding Synchronization Cost

In multithreaded applications, malloc / free or new / delete must synchronize on each call. This synchronization cost can be significant. nedmalloc exists to reduce the synchronization costs of naive implementations and thereby increase performance.

For performance-critical applications, eliminating much of this synchronization cost can be even more beneficial. With CookMem, obtaining large segments using calls such as mmap may require synchronization, but allocations within those segments do not.

Avoiding Individual Frees

There are two sub-cases.

  1. Doing individual frees can reduce performance.
  2. A complex pointer graph containing trees or cycles can make it very difficult to free pointers in the correct order. Yet, the memory has to be released to avoid memory leaks.

Both cases can be addressed easily by using any of the MemContext classes.

Restricting Memory Usage

For long-running programs that take user inputs, it is possible that even when all input values are validated, edge cases in calculations can still cause the program to accidentally request a very large amount of memory and crash. CookMem provides several ways to restrict memory usage. One can set a memory footprint limit or add code to the segment request logic to restrict large memory requests.

Diagnosing and Debugging

CookMem has built-in diagnostic tools that can help gather memory statistics and detect difficult-to-catch out-of-bounds writes without significantly slowing down the program. It also detects attempts to free an allocation more than once. CookMem is not a Valgrind replacement, but in many cases it can help catch difficult bugs.
