CookMem

CookMem is a general purpose memory context / allocator written in C++11 that can be easily and quickly cleaned up by freeing the segments, rather than doing individual frees.

Unlike projects such as nedmalloc which is intended to replace malloc / free in multithreaded applications, this project focuses on the single-thread performance. It is intended to be used within a thread in an MPP process, such that it would not have to pay for the cost of synchronization for most allocations / deallocations. There are other use cases as well.

CookMem separates out the logic for obtaining large segments of memory, to allow users easily creating their flavor of the memory context for their specific needs.

The algorithms and some code used here are based on dlmalloc. I basically took the pain to understand dlmalloc and rewrote the logics in C++. Some key calculations though are kept the same as dlmalloc since there are no points to reinvent wheels.

Performance

The performance of CookMem is comparable if not faster than dlmalloc. There are no locking for dlmalloc or CookMem. For CookMem, I also tested red-black tree (RB-tree) which is the default, and AVL-tree backend.

In the following table, the numbers are in seconds.

Use Cases

Avoiding Synchronization Cost

In multi-threaded applications, malloc / free or new / delete have to synchronize for each call. This synchronization cost can be significant. This is why nedmalloc exists, to reduce the synchronization costs due to naive implementations and thereby increasing the performance.

For performance critical applications though, being able to eleminate much of synchronization cost is even more beneficial. With CookMem, only getting large segments using calls such as mmap would require synchronization, but allocations within the segments do not require synchronizations at all.

Avoiding Individual Frees

There are two sub-cases.

  1. Doing individual frees can cost performance.
  2. If the program has a complex pointer graph, where trees or cycles exist. It becomes very difficult to free pointers in the correct order. Yet, the memory has to be released to avoid memory leak.

Both cases can be easily addressed using CookMem using any one of the MemContext classes.

Restrict Memory Usage

For long running programs that take user inputs, it is possible that even when all input values are validated, there can be edge cases in the calculations that can result in situations where one could accidentally request very large amount of memory that can crash the program. CookMem has a number of ways of restricting memory usage. One could either set the memory footprint limit, or add the code in segment request to restrict large memory requests.

Diagnosing and Debugging

CookMem has built-in diagnostic tools that can help gather memory statistics, and detect difficult to catch out-of-bound writes without significantly slowly down the program. It is certainly not a Valgrind replacement, but in many cases, it is good enough to catch some hard to deal with bugs.
